As of 2026-10-07 · author: the user (sole developer; Claude Code and Codex agents work concurrently on independent features in the same repos; main moves many times a day; every agent rebases on origin/main before opening a PR).

## Goal

Bring complex features back from days to hours: surface unknowns before code, re-plan when reality differs, and measure every phase so each step and model earns its place.

- **Problem today:** simple tasks land; complex ones miss blind spots in planning, drift during execution, and the cause stays invisible.
- **Scope:** a personal, portable harness for Claude Code (Opus 5.5, Fable 5.1) and Codex (Sol 6.1, Astra 6), extendable to Copilot and Cursor; not tied to any company, repo, or plugin; v0 opens PRs on GitHub with `gh`. The harness repo holds only code; every run's record lives in the project it ran in, and derived scores in a per-machine state directory keyed by that project.
- **Done when:**
    1. Harness v0's first runs on real work in each project prove the instrumentation and give the spread for choosing N.
    2. Each later version beats the previous one on deadline-penalized wall time over all assigned runs within the same benchmark tier; done is the gate a run must pass to count as a success, not-done runs, tier upgrades, and escaped defects are guardrails, and rework is a diagnostic.
    3. Every run emits the same per-phase scorecard for any agent, model, and topology.

## Design principles

Smarter models shrink instructions, not checks: the harness keeps its gates and makes every component prove its worth with data.

| Rule | Proof |
| --- | --- |
| **1. Start lean; keep only what moves a metric.** | Each harness component "encodes an assumption about what the model can't do on its own" and can go stale as models improve (Anthropic, harness design for long-running apps). superpowers' writing-plans rewrite for frontier models planned one reported scenario in a quarter of the time (superpowers release notes). |
| **2. Explore first; ask only about preferences,** defaulting and logging any left unanswered. | Codex Plan mode explores repo facts and records unanswered preferences as assumptions (Codex plan template); Claude's feature-dev explores the code before its clarifying questions (feature-dev command). |
| **3. The plan is a living contract:** outcomes, acceptance checks, unknowns, decisions; no code transcripts. | ExecPlans stay self-contained and log every decision (OpenAI PLANS.md). |
| **4. A separate evaluator tests the running system, when needed.** **[Overridden, spec C4: verified by an agent other than the builder; the main agent chooses how]** | Agents grade their own work too kindly, and a standalone evaluator is easier to tune (Anthropic). |
| **5. State lives in files,** so any phase can resume or switch agent. | A fresh agent must be able to restart from the plan alone (PLANS.md). |
| **6. Done is a gate; time is the score.** A run counts only when its acceptance checks pass and you merged it; over all assigned runs within benchmark tier, with not-done and upgraded runs entered at the deadline, wall time decides. | A fast run that shipped the wrong thing is negative value, and scoring quality needs a judge and invites weighting debates; pass or fail from checks already written is objective (this design). |

## Workflow

Seven phases run top to bottom, each borrowed from a cited source, and the task's tier decides which of them run. Phases are contiguous: each starts when the previous one ends; per-milestone verify in L is a sub-step of build, and before the final verify the agent rebases on the integration branch so checks pass against the code that will merge. The unit of measurement is the task, not the session; one task may span many sessions, subagents, or parallel agents, all carrying the same task id.

The right-hand loops send failed checks back to build and broken assumptions back to the plan; the left loop feeds memory into the next run's research. Sources per box: feature-dev, Codex Plan mode, PLANS.md, Anthropic harness design, Claude Code best practices, Codex /goal, Claude Code /goal, GitHub Copilot Memory, Agent Memory Repo. Both current agents offer a native /goal loop; the harness skill implements the build loop generically for agents without one, and an adapter may map it to the native command.

**Triage gate:** a prompt, or a ticket's text pasted verbatim into `request.md` by whatever launches the run, is normalized into the same five fields before anything else happens: goal, outcome, acceptance checks, tier, and source. The task id is `<date>-<slug>` minted by `harness start --new`. `harness start --new` runs in the task's own branch or worktree before the agent is launched, and `harness phase triage enter` is the agent's first phase command; `harness phase` refuses to run on the default branch and records the branch in `state.json`. **[Added, spec C9: `harness doctor` pre-start checks run in `start --new` and at bootstrap; triage refuses until they pass]** Planning starts only when goal, outcome, and one acceptance check can be written without guessing: a missing fact means explore or spike; a missing preference means pick a default and log it as an Unknown; a missing goal means stop and ask. Never default the goal.

**Every tier gets a plan file.** S skips the plan phase, not the plan: triage writes goal, outcome, one acceptance check, tier, and source in five fields. Acceptance checks are numbered C1, C2, … in `plan.md` and runnable where possible (what, expected result, and one fenced command run from the project root whose exit status is the result; the check-text hash covers the check's whole entry: what, expected result, and the fenced command); observational ones go to the evaluator, and in S every check must be runnable, since a check that can only be observed makes the task M. A re-plan may amend them only with a logged Decision that names the check (`Check: C3`, or `Check: goal`).

## Notes and memory

Agents write little, in plain words, and every line shows who, when, and why, so any run can be followed and audited at a glance.

- **One stamped line per entry, under 25 words:** time, agent and model, phase, then what and why.
- **Written as it happens,** never reconstructed, so the record shows the reasoning at that moment.
- **Four kinds, kept apart:** Decisions, Unknowns, and Friction in `plan.md`; Lessons in `.harness/memory/`.
- **One template, validated by the metrics script, never blocking:** `<date time> · <agent/model> · <phase> — <what>. [Why: <why>] [Check: C3] [Cites: path:line] [id: a7f3k2]`; Why is required on Decisions, Check on a Decision that changes a check or the goal, and id on Lessons. Malformed lines are listed on the scorecard.
- **Implementation notes** are one line per milestone when it closes, under that milestone in `plan.md`: what changed, which files. No transcripts.

| Kind | Example line |
| --- | --- |
| Decision | Oct 12 14:05 · Codex/Sol 6.1 · plan — Queue, not polling. Why: polling misses bursts; cron was rejected. |
| Unknown | Oct 12 14:20 · Claude/Opus 5.5 · research — Do auth tokens expire mid-job? Fact; a spike says yes, after 15 minutes. |
| Friction | Oct 12 15:02 · Claude/Opus 5.5 · build — Lost 40 minutes: tests need a local Redis, and setup is undocumented. |
| Lesson | Oct 12 16:10 · Codex/Sol 6.1 · retro — Webhook handlers must be idempotent; the provider retries. Cites: `src/pay/hook.ts:42`. [id: a7f3k2] |

**Memory:**

- `.harness/memory/MEMORY.md` lists areas, not entries, and is read every run (by research in M and L, by the build skill in S, along with the touched areas' files); lessons sit in one file per codebase area, new lines added at the end, with a `MEMORY.md` index in the spirit of Cognition's open Agent Memory Repo.
- **Admission bar, applied by the fresh retro agent after reading the area file:** a lesson is written only if it would have changed a decision or saved time in this run, is not obvious from a minute of reading the code, cites a file and line, and a future agent can confirm or refute it. Dropped: what the code plainly shows, generic practice, one-off incidents with no cause found, summaries of what was done. A line that refines an existing one replaces it; near-duplicates are never added.
- **Cap:** at most 3 lessons per run and about 40 lines per area file; past the cap, the retro agent retires the entry it judges least likely to change a decision, without usage data, to add one.
- **Checked before use:** the agent opens the cited code and fixes or deletes any entry it contradicts (parallel explorers only propose corrections; the phase's controlling skill is the single writer of project memory in that worktree, and retro owns writes after they finish), logging one event through `harness memory kept|fixed|deleted <area>:<id>`, where each lesson line carries a short random id assigned when it is written (`[id: a7f3k2]`, six or more characters so two branches do not collide) and stable across edits and merges, so counters live in events, not memory — the at-use check GitHub chose over offline curation; with citation-checked memory, its coding agent merged 90% of PRs versus 83% without (GitHub, agentic memory system for Copilot).
- **Sweep:** in every harness review, a fresh agent deletes entries whose cited path no longer exists or whose cited code cannot be relocated after a search, fixes relocated citations in place, and merges duplicates, under the same admission bar.
- **Friction is never deduplicated:** it is logged in every run's plan each time it happens; memory holds the lesson once, until the cause is fixed, then it is deleted.
- **One shared store in the project repo:** `.gitattributes` marks `.harness/memory/*.md` `merge=union`, and every rebase goes through `harness rebase`, which commits `.harness/` (a commit confined to `.harness/`, so readiness is unaffected; other uncommitted changes make a new rebase refuse), fetches the configured integration ref, runs `git rebase --merge` onto it so the union merge runs locally under the merge backend, and then, against the merge base it recorded before rebasing under the worktree's git dir, never under `.harness/`, drops by id any lesson line that either side retired and keeps, where both sides carry an id, the text of the side that changed it (the branch's when both did), leaving exactly one line per id, and commits that cleanup, since union can resurrect a line the other side retired, replaced, or deleted when both sides touched the same region; when a rebase it started stops on a conflict, rerunning `harness rebase` after you resolve and `git add` the conflicts (a rerun is taken only while git reports a rebase in progress) skips the commit and the refusal, runs `GIT_EDITOR=true git rebase --continue`, and runs the cleanup once git reports the rebase finished, a further stop being resolved and rerun the same way; while a rebase is stopped nothing but conflict resolution touches that worktree: no note line, no memory edit, and no `harness` command other than plain `harness start` (which writes only to the spool) and the `harness rebase` rerun; the sweep is the backstop. The build skill runs it before the final checks and `harness pr --refresh` runs it before the merge; a rebase that leaves the code tree unchanged keeps readiness. If the forge reports a conflict at merge time, run `harness pr --refresh` again; never resolve memory files server-side, since GitHub's merge ignores `.gitattributes` drivers (community discussion 9288). No locks (the race is between branches, not processes; a lock cannot stop two branches from each appending, and within one worktree the phase's controlling skill is the single writer) and no per-agent stores (they hide contradictions between agents). Lessons about the harness or tooling are not written to memory in v0; they are logged as Friction in `plan.md` and reach you in the PR. The at-use events feed the scorecard (kept, fixed, deleted per area); retirement needs staleness, contradiction, duplication, or cap pressure.

**Run records:** `.harness/runs/<task-id>/` in the project repo, committed, holds everything agents write, keyed by task id; the PR number is an attribute. Phase skills commit `.harness/runs/<task-id>/` alongside their code commits, and `harness pr` commits `.harness/` (run record and memory edits), refusing on uncommitted changes outside it, and pushes before the PR opens, so the PR carries it and only a PR's merge ever brings a run folder onto the integration branch. Derived data stays out of the repo: the hook spool, resolved events, and scorecards live in a per-user state directory keyed by the repo's absolute common dir (`$XDG_STATE_HOME/harness/<hash>/`). A run is merged when its folder is on the integration branch; abandoned when the spool carries an `abandon` close for it; not-done once it passes its deadline or calendar expiry in flight; otherwise in flight. `harness close <task-id> --abandon` records a run with no PR or whose PR closed unmerged, `harness close <task-id> --done` after the merge confirms a scope-reduced run, and both, like `harness defect`, write to the spool. The script scores every registered run on each invocation, idempotently and deterministically, after a plain `git fetch` of the configured integration ref: in-flight and unmerged runs from the spool, merged runs from the integration branch plus the spool; it needs no forge API access and makes no commits. The sweep edits `.harness/memory/` on a branch and opens a PR you merge. The spool and scorecards are per machine and regenerable only from each other, so back up the state directory with the machine. The harness repo holds only code.

```
.harness/project.json   integration remote and default branch, shared_commit, target benchmark tier, N, deadline (hours on the same accumulated clock as the score, which human-wait intervals pause, from the `start` event, per benchmark tier), expiry_days (calendar days from the `start` event after which a run with no terminal disposition is not-done), defect_window_days, alpha, min_gain, memory snapshot commit, baseline and challenger harness commits; [comparison fields reserved for v1, spec C13] written by `harness install`, committed and merged with the `.gitattributes` union line before the first run
.harness/runs/<task-id>/
  request.md        the prompt or ticket, verbatim
  config.json       knobs (phases; per phase agent (none for retro), requested model, effort, topology with role labels; [model, effort and topology recorded only, spec C3] evaluator cadence; plan review), written by triage or later a classifier, plus record (benchmark tier, origin tier, tier, triage's signals, assigned harness commit, predicted knobs)
  research.md
  plan.md           goal · outcome · acceptance checks · tier · source · milestones · decisions · unknowns · friction
  plan.approved.md  snapshot of plan.md written by `harness phase build enter` on the first build entry only; never overwritten
  state.json        task id, branch, current phase, controlling session id (from the agent's session env var, else the adapter's SessionStart record for the same working directory, else null) [overridden, spec C5]; written by `harness start --new` and updated by `harness phase` on entry and exit
  events.jsonl      phase, check (with code-tree hash), review, ready, and pr events from the `harness` CLI
.harness/memory/<area>.md   lessons, long-lived, added at the end, edited only by the rules above; each line carries a short id
$XDG_STATE_HOME/harness/<hash>/   per machine, keyed by the repo's common dir: the hook spool (copies of every CLI event; hook session, subagent, and turn events; start, resume, tier, close, defect, and memory events; per-run copies of request.md and config.json), resolved events, scorecards, and the decision record
```

## Benchmarking

Seven metrics, computed from hooks, git, and file diffs, compare configs on real work. No agent is handed scores: scorecards live outside the repo in the state directory, the retro bundle never includes them, and phase skills are instructed never to read that directory; this is an instruction and data-delivery policy, not an enforced filesystem barrier. **Done is a gate:** a run counts only when the final `plan.md`'s acceptance checks pass, every check added, dropped, or rewritten since `plan.approved.md` is named by a Decision line (`Check: C3`, or `Check: goal` for a changed goal), and you merged it; passing means that for every final check the latest completed attempt before the last `ready` event passed, with a recorded code tree (the commit's tree with `.harness/` removed) equal to the code tree of the tip commit that `ready` names, which must in turn equal the code tree of the merge commit, the last commit in the integration branch's first-parent history that changed `.harness/runs/<task-id>/`, whatever the merge method; after `ready`, a changed code tree, a changed check definition, or a later failed check invalidates readiness, while other commits and pushes confined to `.harness/` do not; `harness pr` refuses to emit `ready` unless, for every final check, the latest completed attempt passed at the tip's code tree with a check-text hash matching `plan.md`; the script diffs the check list between the two files and marks the run not-done if any changed check id, or a changed goal, has no Decision naming it. The CLI flags every deletion or rewrite of an approved check, and every goal change, as a potential scope reduction in the PR (adding a check needs no confirmation); such a run counts as done only if you confirm after the merge that the original outcome still holds (`harness close <task-id> --done`); otherwise it is not-done for its cohort, because a Decision proves traceability, not fulfillment. Wall time within benchmark tier is the score, over all assigned runs with not-done and upgraded runs entered at the deadline value; time among done runs is a descriptive diagnostic; not-done runs, tier upgrades (triage misses), and escaped defects are guardrails; rework, discovery lag, and plan churn are diagnostics that explain why time moved. Timing comes from the outside; unknowns are agent-written, so the evaluator logs any the builder missed as a second count (M and L only).

**Events:** two writers. Hook adapters append session, subagent, and turn events to the repo's spool in the state directory, each stamped with time, session id (or the agent's `agent_id` where the agent models subagents without sessions), parent id, cwd, branch, agent, agent type (the subagent name, if any), `shared_commit`, and any model value the hook delivers, never the arm's commit, which hooks cannot know; **[Added, spec C15: transcript paths on every event]** the adapter keys the directory by `git rev-parse --path-format=absolute --git-common-dir`. The model and cost fields (tokens in, tokens out, cache reads, agent-reported cost) are nullable: null is not zero, `harness score` excludes nulls, and the scorecard shows coverage; each usage value carries a scope, complete or partial (Claude Code's Agent response reports only the final request's tokens), partial values are never summed into run totals, and coverage distinguishes the two. The `harness` CLI writes phase, check, review, ready, and pr events to the run's own `events.jsonl` and appends a copy of each to the spool, writes start, resume, close, defect, and memory events to the spool only, and on `harness phase triage exit` and every `harness tier` appends the run's `tier` and `origin_tier` to the spool, so the spool holds every event of every run, merged or not, and the committed copy serves audit: each phase skill calls `harness phase <name> enter|exit`, which writes `state.json` and the phase event; that exit write is the phase boundary (an enter on a still-open phase, or a `ready`, writes the missing exit first), so phases are contiguous and for S the build starts at triage's exit; `harness check` and `harness pr` refuse after a `ready` unless build is the open phase (entered by `harness phase build enter`, or by `harness pr --refresh` itself before its own work), `harness pr` refuses without a `triage enter`, and the scorecard names each run and boundary that made timing incomplete; `harness review start|end` brackets the optional human plan review (charged, since the review is a knob under test), and excluded gaps belong to no phase. Per-milestone verify in L is a sub-step of build whose evaluator events carry role `evaluator`; the build-to-verify boundary is the final pass. Acceptance checks run through `harness check [--task <id>] <C-id>|--all`, which reads that check's how-to-check command from `plan.md`, runs it itself, records pass or fail from the exit status with the code-tree hash it ran against (the tree with `.harness/` removed) and a hash of the check's text as run, which the gate requires to match the final `plan.md`, requires a clean code checkout outside `.harness/` before and after the run (a result produced while code changed cannot satisfy readiness), and never takes the agent's word; the build skill calls it after every attempt at a milestone's checks, observational checks are recorded only by the evaluator with `--observed pass|fail` **[Overridden, spec C4: by the non-builder verifier]**, and a check with no event counts as failed at the gate. Evaluator note lines always use phase `verify`, even inside L's build, so the evaluator's unknowns stay a separate count. `harness check` writes to the run folder only when the current branch equals the branch in `state.json`, otherwise to the spool with the task id from `--task`, so subagents in temporary worktrees may run it (the Claude Code adapter sets the settings-wide `worktree.baseRef` to `head` **[Overridden, spec C11: not set]**, so delegated worktrees inherit the task's committed feature state, while the launcher fetches the configured integration ref and creates each new top-level task worktree from that ref itself) and their delegated rework is counted; they cannot run `harness phase`, and their other hook events count as orphans. Hooks (Codex hooks, Claude Code hooks) see sessions, subagents, turns, and tool calls, not phases.

**Resolution and adapters:** at scoring, the script resolves spool events to runs by task id where the event carries one, else by branch (recorded in `state.json`), matching events emitted on a detached HEAD during a rebase to the session's last known branch, assigns phases by time from the phase events, maps agent type to the role label in the run's knobs (an unlisted type is kept as role `unconfigured`), and counts the rest as orphans on the scorecard. In v0 model is recorded, not compared: the requested model from the knobs, plus any model value a hook delivers, stored raw with its source and nullable; models are compared only as arms. A phase assigned to a different agent in the knobs is a handoff you perform by launching that agent after the outgoing controller exits its phase with `--handoff`; v0 does not switch agents itself. Each new agent needs only an adapter that emits this schema and fails loudly on format changes. Hook adapters, the CLI, the harness-defined subagent definitions (user-scope files the mixed-run check cannot see, so change them only between comparisons), **[removed, spec C2]** the retro phase's presence, and `hooks/shared-rules.md` (memory admission, replacement, retrieval, and when to run `harness tier`) are shared by both arms and are never part of a challenger, since memory written under one policy is read by both arms and a challenger that dropped retro would win on time at the next run's expense; a change to them starts a new baseline. The challenger wins only if all hold over all assigned runs: its not-done rate and tier-upgrade rate are not worse than the baseline's; its escaped-defect rate, the share of assigned runs with at least one defect event during their `defect_window_days` after merge, resolved or not, is not worse than the baseline's, and no challenger defect is open at decision time; and a one-sided Mann-Whitney test on wall time over all assigned target-tier runs, with not-done and upgraded runs entered at the deadline value so an arm cannot gain by failing hard tasks, rejects at `alpha` (default 0.05) with a median gain of at least `min_gain` (default 20% of the baseline median), its p-value taken from a randomization test that swaps assignments only within their original pairs (which respects the paired assignment and handles the ties deadline imputation creates), implemented in `harness score`, which `shared_commit` pins so it cannot change mid-comparison; a mixed run in the window, any assigned target-tier run with incomplete primary timing (which stays in the cohort), or any session or subagent of an assigned run whose native memory was on or unknown, **[removed, spec C1]** makes the time result descriptive, never confirmatory. Otherwise the result is inconclusive and the baseline stays; there is no extension of a finished comparison, since a second look inflates the error rate, but you may predeclare a new, larger N from the observed spread and start a fresh comparison; a challenger gets one confirmatory comparison, and a repeat of the same challenger is exploratory unless its alpha was pre-split from a declared budget across attempts. What N can detect depends on the workload's spread and on every guardrail, so no power figure is claimed: you predeclare N, the scorecard reports the observed spread, and an inconclusive result keeps the baseline. The rate guardrails are point comparisons that cannot exclude small regressions at small N, and the scorecard says so beside each rate. A comparison's baseline data come only from runs randomized against its challenger. Runs overlap in time and share the machine, test infrastructure, and provider quotas, so a time result holds for this concurrent workload, not in isolation.

**Experiments:** a config is `config.json`, the harness's only per-run input (`project.json` holds per-project constants a classifier never predicts): which phases run, and per phase the agent (except retro, which runs as a subagent of the controlling agent), model, effort, and topology (how many in parallel, with role labels) **[recorded only, spec C3]**, plus evaluator cadence and whether a human plan review happens. Triage writes it today; a classifier may write it later. Change one component per harness commit, the way Anthropic found which parts were load-bearing (Anthropic).

## Routing

Three tiers decide which phases run; a classifier comes only once the data justifies one.

| Tier | Signal | Phases | Evaluator |
| --- | --- | --- | --- |
| **S** | The diff fits in one sentence | Five-field plan, build + checks; the build skill reads memory | None |
| **M** | Multi-file change in code that already exists | Light research, plan, build + checks | One pass at the end |
| **L** | New subsystem, cross-cutting change, or unfamiliar code | Full pipeline, spikes, optional human review | Per milestone |

- **Rules:** skip the plan phase, not the plan file, when the diff fits in one sentence (Claude Code best practices); complexity found mid-run upgrades the tier, never downgrades (superpowers brainstorming), and the agent that finds the complexity runs `harness tier <S|M|L>` on the task branch, which rewrites `tier` in `plan.md` and `config.json`, keeps `origin_tier` from the first triage, appends a tier event, copies `request.md` and `config.json` to the state directory, leaves the current phase open, and never changes the assignment, with a logged Decision; phases the new tier adds run from the current phase onward (S to M adds verify and retro); an upgraded run is never a success in either tier: it is counted as a triage miss, an alarm beside not-done, enters the time comparison at the deadline value, and becomes a label for the classifier; the evaluator runs only where the task sits beyond what the model does reliably solo — its passes are cheap, a few dollars against hour-long build rounds, so the gate is reliability, not cost (Anthropic).
- **Classifier later:** after about 50 labeled runs (my estimate), a classifier predicts `config.json` from `request.md` and triage's logged signals (areas touched, file count, familiarity); ship it only if it beats this table. Three things in v0 make it a drop-in: the harness runs from `config.json`, so a predicted config needs no new plumbing; every run stores the verbatim request, triage's signals, and the predicted config beside the one actually run, and `harness phase triage exit`, each re-triage, and `harness close --abandon` copy `request.md` and `config.json` into the run's entry in the state directory, so the classifier trains on merged folders plus those copies and never on survivors only; and the knob set stays tiny, because the classifier can only recommend configs that have been tried.

## Risks and guardrails

Hands-off runs carry five risks that each need a guardrail.

| Risk | Guardrail |
| --- | --- |
| Hands-off assumptions compound silently | Each is a logged Unknown in `plan.md`; an optional 10-minute plan review stays only if it pays |
| The evaluator approves weak work | Tune its prompt from runs where it disagreed with you; Anthropic needed several rounds (Anthropic) |
| A wrong lesson spreads | Cited code is checked before every use (GitHub) |
| Memory fills with noise | Admission bar and cap at write, citation check at use, sweep at review; friction stays in run records, not memory |
| A lean config under-plans | Mid-run complexity upgrades the tier, never downgrades; not-done runs and escaped defects stay alarms |

**Not in v0:** dashboards, a classifier, budget caps (not portable across agents), tool-call logs, background memory cleanup, swarm orchestration (v0 measures topology only), a ticket adapter, harness-repo memory, cross-project comparison, an interventions count, parent-chain resolution of hook events from subagents in temporary worktrees, and parallel implementers, which superpowers forbids because their edits conflict. **[Also deferred, spec C14: cloud sessions]**

## Build order

Measure from day one: instrumentation comes first, so v0's first runs prove it and give the spread for choosing N.

1. **Instrument:** freeze the seven metrics and the done gate; write one event schema (time, session id, parent id, cwd, branch, agent, agent type, shared_commit, native-memory setting, nullable model and cost fields; **[native-memory setting removed, spec C1; `doctor` event added, spec C9]** session, subagent, turn, start, resume, phase, tier, check with code-tree hash, review, ready, pr, close, defect, and memory events), a hook adapter per agent that fails loudly on format changes, the `harness` CLI, and `harness score`, the metrics script, which you run on demand (at the harness review or any time): it scores every registered run, in-flight and unmerged ones from the spool and merged ones from the integration branch plus the spool, idempotently and deterministically, makes no commits, and validates note lines. Prove it on one task.
2. **Write v0 in its own repo:** `AGENTS.md` as the map, one skill per phase as a plain instruction file the map tells the agent to read from the assigned checkout (no agent-native skill registration), each with a one-line contract ("Research: request → `research.md`"), the fixed `harness` CLI (install, start, phase, tier, rebase, check, review, retro-bundle, pr, pr --refresh, close, defect, memory, score), shared by both arms, `config.json` as the harness's only per-run input, the triage gate, the note and memory formats, and a custom explorer whose prompt reads the project's instruction files, since Claude Code's built-in one skips CLAUDE.md (Claude Code subagents docs). **[Removed, spec C2]** Install once at user scope, outside any comparison: the fixed bootstrap `<harness-path>/hooks/bootstrap.md`, copied into a user-scope file that `~/.claude/CLAUDE.md` imports for Claude Code and appended to `$CODEX_HOME/AGENTS.md` (default `~/.codex`) for Codex, whose guide documents no import mechanism, plus the `harness` command on PATH and the hook entries, dispatchers that read `project.json` and run the pinned shared code, and the harness-defined subagent definitions; each adapter owns its half. Per project, `harness install` resolves and records the integration remote and default branch, writes `.harness/project.json` (that remote and branch, shared_commit, target benchmark tier, N, deadline, expiry_days, defect_window_days, alpha, min_gain, memory snapshot commit, baseline and challenger harness commits) and the `.gitattributes` union line for `.harness/memory/*.md`, and runs each installed adapter's project step, which for Claude Code merges `autoMemoryEnabled: false` into `.claude/settings.json`; **[Removed, spec C1 and C7]** you commit and merge all of it before the first run.
3. **Run and optimize:** two loops. Per task: after build, the build skill runs `harness rebase` and then the final checks (the final verify in M and L); then the skill that owns that last phase before retro (build in S, verify in M and L) runs `harness phase retro enter`, launches the retro agent as a fresh subagent of the controlling agent in the feature worktree **[Overridden, spec C4: a fresh context; the agent chooses how]** (so the retro knob sets its model, and its effort where the agent allows it per invocation, never its agent), in S only when a check failed or friction was logged, and runs `harness phase retro exit` when it returns; `harness retro-bundle` writes its only run-specific input: final plan, approval copy, the check pass and fail events the run already saw, and `git diff <integration-branch>...HEAD`, never a scorecard or any aggregate computed from events; the retro agent also reads the touched areas' memory files and the code it cites; it writes lessons for M and L, and for S only after a failed check or logged friction. After retro returns, the same skill calls `harness pr <task-id>`, which in one invocation refuses unless, for every final check, the latest completed attempt passed at the tip's code tree with a check-text hash matching `plan.md`, commits `.harness/` (run record and memory edits), refuses on uncommitted changes outside it, pushes the branch with `--set-upstream` to the same-named remote branch (`--force-with-lease` after a rebase), opens the PR with `gh`, then appends the `ready` event (naming the tip commit and its code-tree hash, which the gate uses, since a rebase can leave the commit unreachable) and the `pr` event (number, open time), commits them, and pushes again, so a failure before `ready` is simply retried and a failed final push is completed with `git push <remote> HEAD`; before any post-ready edit, rebase, or check, by you or by an agent, build is re-entered with `harness phase build enter` (the owning skill's call, or yours for manual work), which lifts the post-`ready` refusal (the revision's timed start is as the Cost row defines), re-runs `harness check --all`, relaunches the evaluator for each observational check when the code tree changed, and `harness pr`, which opens no second PR, re-emits ready; a revision without that start event makes the run's timing incomplete. Before merging you run `harness pr --refresh <task-id>` in the task's worktree, which writes a `build enter` phase event first (and a `build exit` if it ends without `ready`), runs `harness rebase` and `harness check --all`, and pushes the rebased branch with `--force-with-lease` and re-emits `ready`, all without an agent, when the rebase is clean and every check is runnable and passes, since main can change behavior without a textual conflict; on a conflict, `--refresh` runs `git rebase --abort` before writing its `build exit`, and you launch a revision session, which re-enters build and reruns `harness rebase` itself; you also launch one on a failed check or an observational check; the gate verifies that the last `ready` tip's code tree is what merged; and first `ready` to merge is reported as a diagnostic. The script scores the run once its folder is on the integration branch or the spool closes it. Per project, every few days: you run the harness review by hand from `harness score`, which compares baseline against challenger, and you keep, revert, or try one change per harness commit; the only agent step inside it is the memory sweep, which runs in a fresh worktree on its own branch with the area files and the code and no scorecard, since scorecards are outside the repo, and opens a PR you merge. The review decides a challenger only at its predeclared N, as Fair comparison states.
